# Project Report — Automated Descriptive Exam Assessment Engine with LLM-as-a-Judge

## 1. Evaluation status

The software workflow is implemented, but this repository deliberately does not claim measured human-grading accuracy until five genuine human-graded answers have been entered. Bundled sample answers are test fixtures, not human-study data. No numeric benchmark or bias results are fabricated in this report.

## 2. Problem statement

Manual grading of descriptive university answers takes time and can vary between evaluators. ExamJudge is a decision-support dashboard that compares student answer text with an exam question, model answer, and multi-criterion marking rubric. Its aim is to provide an itemized score sheet, evidence/rationales, conceptual deficiencies, feedback, and machine-readable JSON/CSV exports.

## 3. System architecture

```text
PDF/TXT uploads or pasted answer
  -> bounded text extraction
  -> BLEU / ROUGE / cosine similarity baseline metrics
  -> rubric-aware LLM-as-a-Judge prompt (Gemini, temperature 0.0)
  -> JSON validation, mark-range clamping, half-mark rounding, total recomputation
  -> itemized results, feedback, warnings, JSON and CSV export
```

Offline mode provides a deterministic keyword/overlap baseline for local interface testing. It is not a semantic grader and is not a replacement for the LLM judge.

## 4. Evaluator prompts and calibration

The `prompts/` directory contains the judge system prompt, few-shot scoring examples, calibration criteria, and pairwise A/B position-test prompt. The prompts supply criterion-specific mark maxima, request evidence-linked score justifications, discourage rewarding verbosity, and delimit student text as untrusted input. Temperature is fixed to 0.0; hosted model outputs may still change across calls.

## 5. Benchmark methodology

The dashboard uses the current question, model answer, and rubric from the Grade answers tab. A formal benchmark requires exactly five unique student IDs, five non-empty answers, and one human mark column for each rubric criterion. The app checks missing fields, duplicate IDs, numeric marks, and criterion mark ranges. The user must attest that the marks were independently assigned by a human evaluator; the application cannot audit this declaration. Formal MAE/RMSE/correlation reports are only generated after that confirmation.

## 6. Metrics

- **MAE:** mean absolute total-mark error between the automated judge and human reference.
- **RMSE:** root mean squared total-mark error.
- **Mean signed error:** direction of leniency/severity.
- **Pearson and Spearman:** association and rank association; undefined correlations are shown as n/a.
- **Within-tolerance rates:** proportions within 0.5 and 1.0 marks.
- **Per-criterion MAE:** isolates which rubric dimensions have larger errors.
- **BLEU/ROUGE:** supplementary lexical-overlap baselines; overlap does not equal semantic correctness.

Numeric results should be generated by running the application on the completed human-graded CSV. Five observations are descriptive only and cannot establish broad validity.

## 7. Bias and consistency analysis

The dashboard includes repeatability (standard deviation/range across repeated grading), criterion-order sensitivity (original/reversed/shuffled rubric), verbosity bias (score change after irrelevant filler), pairwise position consistency (winners after swapping A/B positions), pairwise agreement against reference marks, and answer-length/score correlations. Position consistency and agreement with the human reference are reported as separate measures. Human-ranking comparison requires confirmed reference marks.

The included `reports/bias_consistency_analysis.md` documents the methods; numeric tables are generated after a real benchmark is run. A deterministic offline baseline can only validate the test harness; it does not demonstrate LLM fairness.

## 8. Limitations and responsible use

- Five answers are a small sample. Prefer a larger held-out dataset and two independent human graders for a stronger study.
- A user confirmation is not external verification; preserve the marking records and identity/de-identify answer scripts appropriately.
- BLEU/ROUGE may penalize semantically correct paraphrases and can reward keyword overlap without correctness.
- LLMs can make domain errors and hosted outputs are not guaranteed identical, even with temperature 0.0.
- Scanned handwritten PDFs may require OCR; text extraction should be checked.
- Human review remains required before using marks for consequential academic decisions.

## 9. Reproduction

Run locally with `python -m streamlit run app.py`. For the report-generation CLI, first prepare a CSV using the provided template and execute:

```powershell
python scripts/run_reports.py --provider offline --benchmark-csv path	oeal_benchmark.csv --confirm-human-grades
```

Use `--provider gemini` only after setting `GEMINI_API_KEY` in the environment. It makes live API calls and may consume provider quota. To inspect the pipeline using the bundled illustrative fixtures, run with `--demo`; outputs are written to `reports/demo/` and must not be presented as human-study results.
